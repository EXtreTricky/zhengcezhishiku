# 飞书「字段捷径」在政策知识库项目上的局限性分析

> 本文档分析为什么本项目没有采用飞书多维表格的「字段捷径」（Lookup / Formula / 自动化派生字段等）功能，
> 以及自建数据库架构的合理性。

---

## 一、核心架构决策回顾

项目选择了 **自建数据库（`data/db.json`）作为事实源**，Bitable 只作为 **展示层**。

```
政府官网 ──(爬虫)──→ db.json（主数据）──(审批)──→ Bitable（只读展示）
                                    ↑
                              这里是架构决策点
```

如果改用 Bitable 的字段捷径，链路会变成：

```
政府官网 ──(爬虫)──→ Bitable 原始表 ──(Lookup/Formula)──→ 专题展示表
```

这两种架构的根本差异，决定了字段捷径在本项目中的局限性。

---

## 二、具体局限性分析

### 2.1 动态去重失效

**当前实现**：db.json 内存快照 + 字符串比对去重。

```js
// src/db.js - 内存快照去重
if (existingId) {
  console.log(`[crawl] 去重跳过: ${title} @ ${region}`);
  return { success: false, skipped: true, existingId };
}
```

**字段捷径的限制**：Lookup 只能拉取「关联记录的字段值」，无法执行「这条记录是否重复」的判断逻辑。一旦爬取脚本把同一条政策以不同标题多次写入，Bitable 侧无法自动去重。

**结论**：去重必须靠脚本实现，字段捷径无法替代。

---

### 2.2 审批状态无法派生

```js
// 当前：每条 crawl item 有 status 字段
//   status: 'pending' | 'approved' | 'ignored'
//   人工审批后写回 db.json
```

如果用 Lookup 字段关联审批意见，审批动作变成「修改另一张表」——这破坏了审批链路的完整性。Approval 决策本身是业务核心，不应被拆解成两张表的联合查询。

**结论**：审批是独立的业务状态机，字段捷径无法承载。

---

### 2.3 今日增量计算不稳定

```js
// 当前统计口径（按发布日期）：
todayAdded = all.filter(r => normalizePublishedDate(r.releaseDate) === today).length
```

字段捷径里的 Formula 字段如果写成 `=TODAY()-RELEASE_DATE` 来计算「是否今天发布」，会面临两个问题：

1. **公式在筛选时不会触发重算**，导致前端分页结果不一致
2. **公式结果不可写**，爬虫无法把计算结果回写到同一行的其他字段（如 `isToday` 标记）

**结论**：日期判断必须写在 Node.js 层，Field Shortcut 无法可靠实现。

---

### 2.4 多专题表合并查询困难

项目有 10 张专题表（最低工资、平均工资、公积金……），前端一个搜索框要跨表查询：

```js
// 当前：统一查询 db.json，一次返回全部匹配
const results = await policyDb.search({ keyword, category, region });
```

如果用 Lookup 字段关联，需要在 Bitable 里维护一张「总览汇总表」，每次增删改都要同步过去——本质上还是在手动维护一套冗余数据。

**结论**：跨表聚合查询用 Lookup 成本极高，不如主数据库一次查询。

---

### 2.5 爬虫并发写入冲突

```js
// 矩阵巡检：32地区 × 13类目 = 416 个子进程并发写 db.json
// db.js 用文件锁 + syncIfChanged() 保证一致性
```

Bitable 的 API 不支持行级锁，多个子进程同时 `batchCreate` 同一张表会触发竞态条件（rate limit 50 QPS / 并发限）。Lookup/Formula 也不能解决写入冲突问题，反而会增加依赖。

**结论**：高并发写入场景下，自建数据库比 Bitable 更可靠。

---

### 2.6 离线可用性与容灾

```
db.json 落盘 → 可随时备份 / 迁移 / 导入
```

Field Shortcut 的所有数据都依赖 Bitable 在线。网络中断、Bitable 权限变更、应用 token 过期都会导致前端无法渲染。项目架构刻意解耦了这一依赖——主站 `/` 页面完全可以通过静态文件缓存运行。

**结论**：业务关键路径不能绑定单一 SaaS 平台的可用性。

---

## 三、对比总结表

| 维度 | 字段捷径方案 | 本项目方案（db.json 主数据） |
|------|------------|--------------------------|
| 去重 | ❌ 无法实现 | ✅ 字符串比对 + 内存快照 |
| 审批状态 | ❌ 需跨表维护 | ✅ 单表字段 |
| 日期过滤 | ❌ 公式异步、不稳定 | ✅ 服务端精确计算 |
| 跨表搜索 | ❌ 需汇总表同步 | ✅ 一次查询返回 |
| 并发写入 | ❌ 无行锁，易冲突 | ✅ 文件锁 + 原子写 |
| 离线可用 | ❌ 依赖 Bitable | ✅ 数据本地化 |
| 灾备恢复 | ❌ 仅靠 Bitable | ✅ JSON 备份 + 导入 |

---

## 四、什么时候适合用字段捷径

字段捷径适合的场景：

- 同一张表内的简单派生（如「金额 = 单价 × 数量」）
- 跨表 Lookup 展示关联信息（如关联用户姓名、部门名称）
- 单表自动化计算（如逾期天数、是否到期）

**不适合本项目的地方**：

- 爬虫 + 审批 + 多专题聚合的完整业务流
- 高并发写入的分布式数据源
- 对数据主权和离线可用性有要求的场景

---

## 五、结论

**字段捷径适合做「展示层辅助」**，不适合做「业务核心数据源」。

本项目选择 **自建数据库 + Bitable 作为只读展示层** 是正确的架构决策，字段捷径在这个场景下会被证明是画蛇添足。
